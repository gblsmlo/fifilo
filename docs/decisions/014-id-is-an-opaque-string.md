# Decision 014: the id is an opaque string

## Status

Active. Adapted on 2026-09-06 from the reference product's decision 076; the starter keeps the rule and drops the product-specific evidence.

## Context

The question "is UUID the right choice?" arrived in the reference product with
a complaint about the length of ids in URLs. The first measurement dissolved the
premise: there was no UUID in the project, in the sense of a type.

Every primary key was `text('id').primaryKey()`. No `uuid` column, no
`gen_random_uuid()`, no `defaultRandom()`. No `.uuid()` anywhere in the Zod
schemas, tests included. The id primitive validated "trimmed and non-empty" and
nothing else. Four id formats coexisted in the database, and the longest one
was not the UUID: it was an id composed by the application with a semantic
suffix.

The starter is in the same position. `packages/infra/database/src/schema.ts`
declares every primary key as `text('id').primaryKey()`. Better Auth generates
the ids of `users`, `sessions`, `organizations`, `members` and `invitations` on
its own, in its own alphabet. `EntityId` in `packages/core/src/primitives.ts`
is a brand over `string`, produced by `entityId()`, which checks only that the
trimmed value is not empty.

The format of the value was never the contract. This decision writes that down
because the question will come back.

## Options considered

1. **Declare a format.** `.uuid()` in the schemas, `uuid` columns, a regex in
   the primitive. It breaks on day one: Better Auth ids are not UUIDs, and
   most foreign keys point at Better Auth tables.
2. **Swap the generator now** (nanoid, UUIDv7). It does not unify anything
   while a library generates most ids, and it spends the one window to touch
   ids without delivering the property that is missing.
3. **Declare the id opaque**, centralize the generator, and leave the choice of
   algorithm as a replaceable detail.

## Decision

Adopt option 3.

### `EntityId` guarantees provenance, not format

An `EntityId` is a value that passed through `entityId()` in
`packages/core/src/primitives.ts`. Nothing more. No consumer may assume length,
alphabet or version. A regex, a `slice`, a sort or a comparison that depends on
the shape of an id is a finding.

### No `.uuid()` in schemas

Id fields in `packages/core/src/contracts/*` and in capability schemas are
`z.string().min(1)`, as `publicUserSchema.id` in `contracts/users.ts` is today.
`.uuid()` would reject every Better Auth id and would turn a generator swap into
a contract change.

### Primary keys are `text('id').primaryKey()` generated by the application

No id has a database default. The application produces the value before the
insert, and the column type is `text`, so the generator can change without a
migration of columns, foreign keys or indexes.

### The generator lives in one place

No route, use case or repository picks its own generator. Today
`crypto.randomUUID()` is called directly in `packages/auth/src/organization.ts`
and in `packages/observability/src/context.ts` and `tracing.ts`. The first
capability that needs an application-generated id extracts a single generator
into `packages/core` and the existing call sites move to it. Dispersion is what
makes a swap expensive without needing to be.

Request ids in observability are outside the entity rule: they never reach a
URL or a screen, but they use the same generator for the same reason.

### Id format is not a capability decision

If the generator changes one day, it changes in one place. A capability that
needs a different format for its own ids has a reason to record here, not a
local exception.

## Consequences

- There is a written answer to "why UUID?": it is not UUID, it is an opaque
  string, and the generator is a replaceable detail.
- More than one id format circulates, because Better Auth generates its own.
  That is an accepted consequence, not an oversight.
- A URL length complaint is addressed to how the id is composed, not to the
  generator, until the composition is ruled out.
- Extracting the generator is a prerequisite of any future migration and is
  cheap while the call sites are few.

## Revisit when

- Someone needs the format: if a consumer must validate, sort or derive
  anything from the value of an id, the first clause broke and this decision
  is rewritten, not worked around.
- Index locality or creation-order sorting becomes a measured problem on a
  large table. UUIDv7 gains a reason of its own, independent of length.
- Better Auth stops generating the ids of its tables, or the project leaves
  it. The constraint that prevents unifying formats falls.
- Real data appears in volume before any migration. The cost of rewriting
  existing rows and foreign keys must be re-estimated.
